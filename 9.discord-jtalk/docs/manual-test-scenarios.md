# 実機テストシナリオ(人が実行)

`pytest` によるユニットテストはロジック(優先度制御・キュー処理・メッセージ分岐)のみを
検証しており、実際の音声出力やDiscord接続は保証しない(詳細は `CLAUDE.md` の
「テスト方針」参照)。以下は Raspberry Pi 実機 + スピーカー + Discord チャネルで
人が確認するための最低限のシナリオ。

前提: `DISCORD_TOKEN` を設定して `python3 src/home.py` を起動済みであること。

## ケース1: 基本のテキスト読み上げ

**操作手順**
1. 家族用チャンネルに任意のテキスト(例:「こんにちは」)を投稿する

**確認観点**
- 数秒以内にスピーカーから投稿内容が読み上げられる
- botがエラーで落ちない、Discord側にも異常な反応がない

## ケース2: YouTube再生とキューイング

**操作手順**
1. YouTube URLを1件投稿する
2. 再生中(終わる前)に、別のYouTube URLをもう1件投稿する

**確認観点**
- 1件目の音声が再生される
- 2件目は1件目の再生が終わるまで待機し、その後順番に再生される(同時に音が重ならない)

## ケース3: 優先度プリエンプションと「停止」

**操作手順**
1. YouTube URLを投稿し再生を開始させる
2. 再生中(終わる前)に、任意のテキストを投稿する
3. 読み上げが終わった後、再度YouTube URLを投稿し再生を開始させる
4. 再生中に「停止」とだけ投稿する

**確認観点**
- 手順2: YouTube再生が中断され、読み上げが優先して流れる(読み上げがYouTube再生に割り込む)
- 中断されたYouTube再生が、読み上げ終了後に自動で再開しないこと(現状の実装は再開しない仕様なので、想定通りか確認)
- 手順4: 「停止」投稿直後に音声が止まり、キューに残っていたURLも再生されないこと

## 全ケース共通で確認すること

- 各ケースの実行後、`open_jtalk` / `aplay` / `mpv` のプロセスが残留していないか(`ps aux` 等で確認)
- bot本体(`home.py`)のプロセスが落ちずに動き続けているか
